# 实施计划：规则就绪与目录

依据：[规格](spec.md)，基线 main `ad01dc7`。本轮规格、离线测试及用户明确授权的三项政策生产修复均已实施；其他基线默认参数保持原约束。任务和结果分别见 [tasks.md](tasks.md)、[validation.md](validation.md)。

## 实现入口与职责

RuleCandidateAnalyzer、RuntimeSelectorPolicy、CaptureRuleSafetyPolicy、RuleValidator、RuleCatalogSnapshot、BuiltinRuleCatalog、CompositeRuleCatalog；启用消费方为 RuleCaptureCoordinator。

目录仅派生规则，引擎负责会话与动作决定，平台负责 Android 节点及动作证据。测试从现有公开入口或同模块内部策略入口驱动，不通过反射改写业务状态。沿用现有模块、端口和数据模型，不引入通用框架或存储迁移。

## 已复现差异与已实施修复

修复前 RR-01 的 10 个反例表明，纯文本、纯描述及文本加描述在无稳定结构时可能 READY，统一校验未拒绝相同输入。用户明确授权后，已收紧分析器的全部强选择器条件，在统一规则校验处覆盖每个选择器及所有目录入口，并让 RuntimeSelectorPolicy 的稳定判断排除空白 ID；保留样本、存储和开关，不改变公开端口。

静态差异不是执行结果。先核对反例输入满足前置条件，再执行并保存断言失败；若失败出自测试环境或替身，修正测试后重跑。目标契约失败不能通过降低预期、忽略用例或标记预期异常变成通过。

## 实施顺序

1. 规格、政策和边界落盘，建立 AC → 任务 → 用例 → 结果追踪。
2. 按任务表先纯函数、后目录/策略、再引擎和平台/集成，复用既有测试支撑；三项政策各有独立反例。
3. 使用虚拟时间和明确屏障控制并发，阈值覆盖之前、相等及之后；替身只提供输入、故障和提交时刻，不复制业务判断。
4. 执行相关专项测试和既有 75 例，分别统计成功、失败、错误、跳过；检查器、构建、Lint 独立记录。先保存失败报告，再运行子集，避免覆盖证据。
5. 保留修复前反例证据，在明确授权后实施最小生产修复并重跑完整套件。本轮 201 例全部通过，其中本包 32 例、原有 75 例保持通过；独立静态评审六个生产修复文件未发现问题。规格及报告检查最终结果以验证记录为准。

## 测试与证据

现有 JUnit 4、coroutines-test 和 Robolectric 4.17 已足够；平台测试固定 SDK 36，必要的故障 Shadow 仅放测试源码。选择器查询、观察、记录和存储通过现有端口控制。长期收集作用域由测试清理，取消不能吞掉。

新增必需用例仅在已实现并核对真实方法标识后登记 `.ci/required-tests.json`，保留既有 75 例及失败/跳过/报告缺失阻断。若专项仍失败，CI 结论必须保持失败，不通过排除用例制造绿色结果。

本轮每条 AC 的已列场景及必要回归通过，三项已批准政策偏差已闭环；P2 本地离线验收通过。独立静态代码评审不能替代独立 QA。Robolectric 不证明真实设备、事件投递或点击效果。远端设置、依赖、构建配置、设备验证及已停止的 SDD-001/T-12 不在实施范围；不提交生成报告、APK 或诊断日志。
